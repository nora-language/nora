# Investigation: FFI BorrowToRaw Double-Pointer Generation on Arrays & Allocated Pointers

**Status**: Completed (Fixed in Compiler)
**Date**: 2026-07-07

## Problem
The `nora_wgpu` project's `triangle` example failed to run following the Nora compiler update `16f33d8 Fix FFI dangling pointer bug and introduce compiler intrinsic attributes`. 
Two severe issues emerged during execution:
1. **WebGPU Validation Error**: `vkCreateGraphicsPipelines` complained that the vertex buffer format was undefined (`VK_FORMAT_UNDEFINED`), meaning `WGPUVertexAttribute` data was corrupted or unreadable.
2. **Invalid Texture Panic**: A hard panic (`thread '<unnamed>' panicked at src\lib.rs:4293:40: invalid texture`) occurred deep inside `wgpu_native` when dropping textures or attempting to present/draw.

## Reproduction
1. Sync `nora_wgpu` to a commit using `ffi.BorrowToRaw` on arrays or allocated pointers.
2. Compile and run `nora run --example triangle` on the latest compiler.
3. The program panics or throws immediate validation errors before/during the render loop.

## Root Cause
The root cause lies in how the `borrow_to_raw` and `mut_borrow_to_raw` intrinsics in `pkg/codegen/hir_codegen.go` determine whether to take the address of an operand.

The recent compiler patch intended to fix FFI dangling pointers by taking the address of borrows (`&argStr`) when passed to `BorrowToRaw`. 
The `hir_codegen.go` handles this via the `shouldPassByPointer(unwrapped)` check:
- **For Structs** (e.g., `sys.ShaderModuleDescriptor`): `shouldPassByPointer` correctly returns `true`, and the codegen generates `((void*)(struct_ptr))`. This successfully passes the correct C-pointer.
- **For Arrays and Allocated Pointers** (e.g., `f32[]` or `@sys.SurfaceTexture`): `shouldPassByPointer` evaluates to `false` because primitive and array pointers are not considered "structs" that need implicit C-pointer conversion (they are already native pointers). Consequently, the codegen falls back to taking the address of the variable: `((void*)(&(array_ptr)))`. 

This resulted in double-pointers (e.g., `float**`, `sys_WGPUVertexAttribute**`, `sys_WGPUSurfaceTexture**`) being passed to the `wgpu_native` C-API, which expected single pointers.
- WebGPU interpreted the pointer-to-pointer as the actual array data, reading garbage for the pipeline's vertex layouts (leading to `VK_FORMAT_UNDEFINED`).
- `wgpuSurfaceGetCurrentTexture` wrote the surface texture output over the double-pointer itself instead of the allocated struct (leading to the `invalid texture` panic upon drop).

## Fix
The compiler's intrinsic code generator (`pkg/codegen/hir_codegen.go`) was patched to properly identify and handle types that are already native C-pointers. 

Specifically:
1. It now evaluates `g.isPointerTypeInC(unwrapped)`. If the argument type evaluates as a C-pointer (such as an array slice), it bypasses the `&(%s)` generation and casts the pointer directly `((void*)(%s))`.
2. It strips away internal `AddressOf` AST nodes that are automatically generated by the Nora language when developers use the mutable borrow syntax (`&arr`). This prevents the generated C string from evaluating to `&(arr)`, keeping it as a single-level pointer.

With these changes, developers can safely and ergonomically use `ffi.BorrowToRaw` and `ffi.MutBorrowToRaw` on any pointer-like type without worrying about double-pointer corruption.

## Validation
1. A reproduction regression test was added at `pkg/cmd/test/repro_ffi_borrow_double_pointer/main.nr`. It explicitly checks that `ptr(arr) == ffi.BorrowToRaw[T](#arr)` and `ptr(arr) == ffi.MutBorrowToRaw[T](&arr)`.
2. The full compiler integration test suite (`nora.exe test`) passes without regressions.
3. The `nora_wgpu` project's `triangle` example successfully enters the render loop without throwing validation errors or panics while utilizing the FFI borrow intrinsics.
