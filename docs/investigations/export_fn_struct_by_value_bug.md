# Export Function Struct-by-Value Codegen Bug

## Status
Resolved

## Problem
When exporting a Nora function to C using the `pub export fn` syntax, the generated C code incorrectly translates Nora struct arguments passed by value into C pointer arguments. This causes a type collision with the generated C header file, where the function signature correctly expects the struct by value, while the C implementation file generated by Nora incorrectly expects a pointer to the struct.

For example, when wiring up WebGPU's log callback:
`pub export fn wgpu_log_callback(level: i32, message: sys.StringView, userdata: ptr)`

The generated `out.h` correctly contains:
`void wgpu_log_callback(int _level, sys_WGPUStringView message, void* _userdata);`

However, the generated C implementation in `out_pkg_main.c` incorrectly contains:
`void wgpu_log_callback(int _level, sys_WGPUStringView* message, void* _userdata) { ... }`

This results in a compilation failure when the C compiler attempts to compile the generated output:
`error: conflicting types for 'wgpu_log_callback'`

## Reproduction
1. Define a struct in a package (e.g., `StringView`).
2. Define a function in Nora using `pub export fn` that takes this struct by value.
3. Compile the package.
4. The C compiler will fail with a `conflicting types` error because the generated `.c` file uses a pointer for the struct parameter, while the generated `.h` file uses a value type.

## Root Cause
The root cause involved multiple codegen discrepancies where `fn.IsExport` was not being respected:
1. **Parameter Lowering:** In `pkg/codegen/generator.go` (`genFunction`) and `pkg/codegen/hir_codegen.go` (`genFuncDef`), the parameter lowering logic (`cParamType`) assumed the function was not external, defaulting to pointer coercion for structs. This caused the C implementation file to expect pointers instead of value types.
2. **Internal Operand Typing:** In `cTypeOfOperand` (`hir_codegen.go`), internal variable and parameter types did not check if the current function was exported. As a result, variables inside the exported function were treated as pointers instead of values, generating incorrect member accesses like `message->length` instead of `message.length`.
3. **Internal Calls:** When Nora internally called an exported function (`case *hir.Call:`), the `isExtern` logic didn't account for `IsExport`. The compiler injected the internal `_env_ptr` parameter and passed structs by reference instead of using the strictly defined C-compatible signature.

## Fix
The `pkg/codegen` logic was thoroughly updated to respect `fn.IsExport`:
- Modified `genFunction` (`generator.go`) and `genFuncDef` (`hir_codegen.go`) to pass `fn.IsExport` into `cParamType`, ensuring exported functions retain value semantics for struct arguments in the C implementation.
- Updated `cTypeOfOperand` to detect if the current function is exported (`isExtern`). This aligns internal variable typing with the C-ABI parameter types, preventing incorrect pointer-based member accesses.
- Updated `genCall` (`case *hir.Call:`) to check for `IsExport` alongside `IsExtern`, preventing the injection of `_env_ptr` and maintaining correct value-passing semantics when Nora code internally invokes an exported function.

## Validation
A regression test (`export_struct_by_value.nr`) was created in `pkg/cmd/test/export_struct_by_value/` verifying that a `pub export fn` taking a struct by value compiles properly and can be called from within Nora without `_env_ptr` errors. The full Nora compiler test suite (`go test -v ./pkg/cmd/nora`) passed successfully with 0 regressions.
